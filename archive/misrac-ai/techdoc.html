📌 1 · Overview
System design and components of the MISRA-C:2012 static analysis checker
ℹ️
Purpose of this document
This technical document describes the architecture of the MISRA-C:2012 rule checker: the problem it solves, the system components, how the implementation is organized, and how correctness is validated.
⏱️ Problem Statement

Hand-checking C source against the 143 MISRA-C:2012 directives and rules is slow, inconsistent, and not auditable. Teams need a deterministic, machine-readable checker that integrates into CI.

🎯 Scope

This document covers the static-analysis engine, rule catalogue, and report generation. It does not cover runtime testing, dynamic analysis, or the build system itself.

🔄 Objectives

Provide zero-dependency, repeatable rule checks, human-readable HTML/JSON reports, and a plugin point for new rules without changing the core pipeline.

📚 Audience

Tooling engineers, embedded C contributors, and QA leads who need to understand, extend, or operate the checker.

🏗️ 2 · System
Component architecture, module responsibilities, and data model
🧩 Key Modules
Parser src/parser
  • Tokenizes and builds a typed AST from C source
  • Preserves file/line spans for every node
Rule Engine src/engine
  • Walks the AST and dispatches to registered rules
  • Collects violations with severity and evidence
Rule Catalogue rules/
  • One module per MISRA-C:2012 rule or directive
  • Declarative metadata (id, category, message)
Reporter src/report
  • Renders standalone HTML and machine JSON
  • Sidebar navigation generated from violation set
📦 Data Model
src/model.py
1class Violation:
2    rule_id:    str      # e.g. "Rule 11.3"
3    severity:   Severity # Mandatory | Required | Advisory
4    file:       Path
5    line:       int
6    message:    str
7    evidence:   str      # offending snippet
PAIN
Manual MISRA review is slow and non-deterministic across reviewers.
▼
ROOT
No shared, machine-readable model of rules and AST evidence.
▼
IMPACT
Compliance cannot be gated in CI; audits are hard to reproduce.
▼
ACTION
A deterministic engine walks a typed AST and emits reproducible violations + reports.
🔧 3 · Implementation
Code layout, configuration, and known gotchas
⚠️
Gotcha: macro-expansion order
Rules that inspect types must run after macro expansion. Place them in phase 2; running them in phase 1 produces false positives on #define wrappers.

🧩 Adding a New Rule
rules/rule_11_3.py
1from src.engine import Rule
2
3class Rule_11_3(Rule):
4    id = "11.3"
5    def visit_Cast(self, node):
6        if node.is_pointer_to_object_vs_pointer_to_function:
7            self.report(node, "Cast shall not…")
✅ Do
  • Keep rule modules side-effect free
  • Always attach a line number to evidence
  • Register rules via the catalogue decorator
❌ Don't
  • Don't mutate the AST in a rule
  • Don't hardcode paths — use config
  • Don't skip the macro-expansion phase
